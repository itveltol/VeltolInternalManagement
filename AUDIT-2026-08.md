## Összefoglaló

A projekt szerkezete jó: következetes feature-slice felépítés (`api/` → `services/` → `components/`), injektálható API-client réteg, ami tesztelhetővé teszi a szolgáltatásokat, kiváló migrációs kommentárok és **hibátlan i18n** (798 kulcs mindhárom nyelven, nulla eltérés). Ez átlag feletti egy belső eszközhöz.

Három terület viszont éles kockázatot hordoz:

1. **Biztonság** — két kritikus, távolról kihasználható RLS-hiba. Bármely bejelentkezett felhasználó adminná teheti magát. A szerveroldali szerepkör-ellenőrzések emiatt kozmetikaiak: a publikus anon kulccsal a támadó közvetlenül a PostgREST-tel beszél.

3. **Igazság-források duplikációja** — a „projekt készültség" háromféleképp van kiszámolva (SQL trigger, TS service, checklist), és **már most eltérnek egymástól**.

Jó hír: a `.env*` fájlok **nincsenek** a git-ben, soha nem is voltak (`.gitignore:26` + a teljes history ellenőrizve). A `.next/` és a `tsconfig.tsbuildinfo` is helyesen ignorálva.

# 1. BIZTONSÁG — azonnali teendők

## 🔴 KRITIKUS-1 — Bárki adminná teheti magát

`supabase/migrations/20260622000001_create_profiles.sql:58-62`

```sql
-- Users can update their own profile (except role — admin update policy covers role changes)
create policy "profiles: update own"
  on public.profiles for update
  using (auth.uid() = id)
  with check (auth.uid() = id);
```

A komment azt állítja, hogy a `role` ki van zárva. **Nincs.** A Postgres RLS sor-szintű, nem oszlop-szintű. Nincs `GRANT UPDATE (oszlop, ...)` megszorítás (mind az 56 migrációban nulla `grant`/`revoke`), és nincs `BEFORE UPDATE` trigger sem.

Kihasználás — bármely bejelentkezett felhasználó, böngésző konzolból, a bundle-ben már benne lévő publikus kulccsal:

```js
await supabase.from('profiles').update({ role: 'admin' }).eq('id', myUserId)
```

Ezután az `is_admin()` igazat ad → teljes portfólió (`value_eur`), minden dolgozó személyes adata, törlési jogok mindenre, és a `requireAdmin()` akciók (`inviteUser`, `deleteUser`) — amelyek a **service-role klienst** használják. Teljes kompromittálódás a legalacsonyabb `viewer` fiókból is.

Ugyanez érinti a `registered_at` és `medical_exam_expires_at` mezőket — a felhasználó saját orvosi vizsgálat-lejáratát is átírhatja.

**Javítás:**

```sql
create or replace function public.prevent_self_role_change()
returns trigger language plpgsql security definer set search_path = public as $$
begin
  if new.role is distinct from old.role and not public.is_admin() then
    raise exception 'role changes require admin';
  end if;
  return new;
end $$;

create trigger profiles_guard_role
  before update on public.profiles
  for each row execute function public.prevent_self_role_change();
```

Öv és nadrágtartó: `revoke update on public.profiles from authenticated;` majd `grant update (first_name, last_name, phone, avatar_url) on public.profiles to authenticated;`

## 🔴 KRITIKUS-2 — `pas_write`: bárki átírhatja vagy törölheti a teljes státuszmátrixot

`supabase/migrations/20260624000006_matrice_status.sql:89-93`

```sql
create policy "pas_write" on public.project_activity_status
  for all to authenticated
  using (true)
  with check (updated_by = auth.uid());
```

Három baj egyszerre:

1. A `for all` a **DELETE**-et is lefedi. DELETE-nél a `WITH CHECK` **nem értékelődik ki**, csak a `USING`, ami `true`. Tehát bárki lefuttathatja: `.from('project_activity_status').delete().neq('project_id', 0)` → az egész cég státuszmátrixa törlődik. Ez a tábla hajtja a `progress_pct`-t és az aviz-lejárati emlékeztetőket.
2. `USING (true)` UPDATE-nél: bárki módosíthat bármely projekt bármely soráját. A `WITH CHECK (updated_by = auth.uid())` csak arra kényszeríti a rongálót, hogy a saját ID-jét írja be — ez audit-mező, nem jogosultsági kontroll.
3. Az alkalmazásrétegben sincs védelem: `src/app/[locale]/(app)/matrice-status/actions.ts` — a `setCellStatus` (85. sor), `setProjectProgressManual` (104.) és `syncChecklistFromMatriceCell` (136.) mind `requireAuth()`-ot hív, **szerepkör-ellenőrzés nélkül**, ellentétben minden más feature-rel, ami `requireMutator()`-t használ. Tehát egy `viewer` vagy `outfield_worker` a **normál felületen keresztül** átírhat projektstátuszokat, exploit nélkül.

**Javítás:**

```sql
drop policy "pas_write" on public.project_activity_status;

create policy "pas: mutators insert" on public.project_activity_status
  for insert to authenticated
  with check (public.can_mutate_projects() and updated_by = auth.uid());

create policy "pas: mutators update" on public.project_activity_status
  for update to authenticated
  using (public.can_mutate_projects()) with check (updated_by = auth.uid());

create policy "pas: admin delete" on public.project_activity_status
  for delete to authenticated using (public.is_admin());
```

+ a három matrice akció átállítása `requireMutator()`-ra.

# 3. ARCHITEKTÚRA

## A rétegzés jó, de három helyen szivárog

A konvenció (route action → service → api client → Supabase) 15-ből 14 akciófájlban következetes, és **egyetlen komponens sem importál közvetlenül Supabase-t**. Ez erős.

Kivételek:

- `matrice-status/actions.ts:143` — nyers `supabase.from("project_checklist_items").update(...)`, megkerülve a `supabaseChecklistClient`-et. Ugyanígy a 105. sor a `projects`-en.
- `search/action.ts:12-28` — a teljes keresés három inline PostgREST query egy szerver akcióban; nincs api client, nincs service
- `dashboard/action.ts` — minden lekérés inline; nincs `features/dashboard/api/`
- `projects/actions.ts:64-158` — az `extractProjectPayload` nem triviális domain-szabályokat tartalmaz (contract-type all-or-nothing fallback, residential → `project_type = null`). Ez `features/projects/services/`-be való, ahol unit-tesztelhető.

Fordítva: **8 feature service-e 100%-ban átpasszoló**. A `projectService.ts` 40 sora tisztán `return client.getProjects()`. ~250 sor indirekció nulla viselkedéssel. Ezeket törölni kell — csak a stack trace-t hosszabbítják.

## Séma-problémák

**Hiányzó indexek:**

| Hiányzik | Miért fáj |
|---|---|
| `projects (manager_id)` | **Minden projektolvasás RLS policy-je** ezt használja (`...027:8`). Jelenleg seq scan policy-kiértékelésenként. |
| `projects (team_id)` | `PROJECT_SELECT`-be beágyazva, soha nem indexelve |
| `documents (responsible_id)`, `teams (lead_id)`, `vacation_requests (approved_by)` | FK-k index nélkül |

**Ellentmondó FK-k:**

1. `documents.created_by uuid not null references profiles(id) on delete set null` (`...010:20`) — `NOT NULL` + `ON DELETE SET NULL` önellentmondás.
2. `projects.updated_by → profiles(id)` **`on delete` záradék nélkül** = `NO ACTION`. Ugyanez a `project_activity_status.updated_by`-nál.

A `profiles.id references auth.users on delete cascade`-del együtt ez azt jelenti, hogy **a `deleteUser` FK-hibával elbukik minden olyan felhasználónál, aki valaha szerkesztett projektet vagy Matrice cellát** — azaz minden adminnál és PM-nél. Az akció elkapja és `errorGeneric`-et ad, tehát az admin annyit lát: „valami hiba történt". → `on delete set null` mindkét oszlopon.

**Enum-kavarodás:** a `project_type` enum ma 9 értéket tartalmaz, amiből **4 halott**. A `...052`/`...053` migrációk dokumentálják, hogy az enumot román szöveggel seedelték (`'CEF cu BESS'`), ami soha nem egyezett a legördülő értékeivel (`'CEF+BESS'`) — így az `fn_auto_na_on_type_change` **2026-06-24 és 07-30 között egyetlen valós projektre sem illeszkedett**. A javítás hozzáadta az értékeket, de mindkét írásmódot bent hagyta.

**Trigger-lavina:** a `trg_recompute_project_progress` `for each row`, és minden hívása végigpásztázza a projekt összes ~100 tevékenységét. Az `fn_auto_na_on_type_change` tömeges upsertje projektmentésenként ~9 újraszámolást indít; az `applyFolderScanSuggestions` (`projects/actions.ts:363-382`) egyesével hívja a `setCellStatus`-t és az `upsertChecklistItem`-et, mindegyik újabb teljes recompute-ot indítva. → `for each statement` + transition table, és batch upsert.

**RLS policy inkonzisztencia:** öt különböző minta ugyanarra a szándékra. A `projects` és `documents` a `can_mutate_projects()` security-definer helpert használja; 10 másik tábla ugyanazt az inline `exists (select 1 from profiles ...)` alkérdést másolja soronként újrafuttatva; a `project_activity_status` pedig `using (true)`. Egységesíteni kell a helperre.

## Egyéb architekturális megjegyzések

- **Nincs multi-tenancy és nincs is előkészítve.** Nulla `org_id`/`tenant_id` az egész kódbázisban. - **A `["admin","project_manager"].includes(role)` ellenőrzés 19 helyre van bemásolva.** Ki kell emelni: `src/core/auth/permissions.ts` nevesített képességekkel (`canMutateProjects`, `canManageUsers`).
- **Az `app_role`-nak 6 értéke van, de a kód csak kettőre ágazik el.** A `site_engineer`, `finance`, `viewer`, `outfield_worker` viselkedésileg azonos (csak olvas).
- **Nincs audit log.** Az `updated_by`/`updated_at` az egyetlen nyom, és a `fn_recompute_project_progress` szándékosan nem nyúl hozzá — tehát a trigger által hajtott státuszváltozások nyomon követhetetlenek.

- **Proxy: két Supabase auth kör navigációnként.** A `proxy.ts:78-88` `getUser()`-t (hálózati hívás) **és** egy `profiles` selectet futtat minden nem-statikus kérésen, majd a page render újra ugyanezt. Szűkítsétek a matchert és adjátok át a feloldott usert/role-t request headerben.
- **Locale-vesztő navigáció:** az `@/i18n/navigation` létezik, de csak 9 fájl használja, míg **41 közvetlenül a `next/navigation`-t** importálja. Három konkrét bug: `PortfolioGanttShell.tsx:147`, `ProjectPhaseGanttShell.tsx:54`, `TeamDetailShell.tsx:63` — locale-prefix nélküli `router.push`.
- **A `folderProvider.ts` nincs valóban absztrahálva:** az `if (AZURE_CLIENT_ID)` elágazás háromszor van lemásolva, nincs `FolderProvider` interfész. A `getGraphToken()` minden híváskor friss tokent kér (~1h érvényes, nincs cache). A lokális stub a `~/Desktop/VeltolProjects`-be ír — Vercelen ez ephemeral, és a hiba elnyelődik.
- **A cron route-ok a legjobban strukturált integrációk** (valódi auth, megosztott service-ek) — de az e-mailek **szekvenciális await hurokban** mennek hibakezelés nélkül: egy Resend-hiba megszakítja a futást, a maradék manager semmit nem kap, és újrapróbálásnál duplán megy ki. `Promise.allSettled` + `reminder_log` tábla idempotenciához.

- **A táblasorok csak egérrel használhatók.** `ProjectsTable.tsx:248-252` `onClick`-et tesz egy csupasz `<tr>`-re `tabIndex`, `role`, `onKeyDown` nélkül. Az egész appban `grep "tabIndex|role=\"button\"|onKeyDown"` → **2 találat**. Billentyűzettel vagy képernyőolvasóval **nem lehet projektet megnyitni a listából**.
- **A fókuszgyűrűk le vannak szedve.** 40× `outline-none` vs. 13× `focus-visible`. A `MatriceCell.tsx:79` `focus:outline-none`-t tesz a státusz-dropdown triggerére pótlás nélkül — a fő képernyő fő vezérlője láthatatlan billentyűzet-fókusszal.
- **Szinte nulla ARIA:** `aria-label` ×6, `aria-expanded` ×6, `aria-hidden` ×4 — 20 db ikon-only gomb mellett, amik csak `title`-re támaszkodnak.
- A validáció csak HTML5 `required`, tehát a hibaszöveg a **böngésző** nyelvén jelenik meg, nem az appén. Nincs mezőszintű hibamegjelenítés és nincs scroll-to-first-error a hosszú `AddProjectDialog`-ban.

### 17. Az üres állapotok zsákutcák

Nincs tooltip komponens, nincs onboarding, nincs first-run élmény. Az üres állapotok egy halvány mondat egy `<td>`-ben, gomb nélkül.

Kritikus részlet: a táblák **ugyanazt** az üzenetet mutatják akkor is, ha az adathalmaz valóban üres, és akkor is, ha a szűrők kizártak mindent (`ProjectsTable.tsx:240` a már szűrt tömb hosszát nézi). Öt szűrővezérlő fölötte — aki túlszűr, azt kapja, hogy „nincsenek projektek", és nincs „szűrők törlése" kiút.

Felderíthetetlen mechanikák magyarázat nélkül:
- `ProjectsTable.tsx:269-278` a szerződéstípusokat egybetűs színes körökként (P/E/M/R) rendereli, csak hover-title-lel. **Nincs jelmagyarázat** — pedig a Matricének van rendes `MatriceLegend`-je.
- Az elrejtett projektek: az X gomb szerveroldalon perzisztálja az elrejtést, de semmi nem jelzi, hogy vannak elrejtett projektek, vagy hogy hány.
- A dashboard fő CTA-ja „Projekt hozzáadása", de csak a `/projects`-re linkel — nem nyitja meg a dialógust.

# 5. AMI VALÓBAN JÓ

Ezeket érdemes referenciamintaként megőrizni:

- **i18n:** pontosan 798 kulcs `en`/`ro`/`hu`-ban, **tökéletes kulcs-paritással**. Bedrótozott UI-szöveg csak márkanév.
- **Optimista UI helyes rollbackkel** a `MatriceShell`-ben — csak egy toast hiányzik róla.
- **Az `ApiClient` interfész-varrat** — minden service tesztelhető DB nélkül. Ritka egy belső appban.
- **A `Button` primitív** — rendes `focus-visible` gyűrűk, `aria-invalid` kezelés, értelmes méretskála.
- **A `ChecklistTable` dirty-state követése** — az egyetlen hely, ahol a mentetlen munka védve van.
- **Származtatott state renderelés közben** (`ProjectsTable.tsx:86-99`) — helyes React 19 idióma, elkerüli az effect-vízeséseket.
- **`computeRange` (`PortfolioGanttChart.tsx:67-108`)** — átgondolt outlier-vágás, hogy egy távoli fázis ne lapítsa össze az idővonalat, kiváló magyarázó kommenttel.
- **A migrációs kommentárok** — a legtöbb elmagyarázza a „miért"-et, több pedig előre dokumentálja az ismert duplikációs kockázatot.
- **A `redirectPreservingCookies` (`proxy.ts:22-26`)** — helyesen viszi át a `Set-Cookie`-t a redirectekre; ezt a legtöbb kódbázis elrontja.
- **A `/api/vacation/[id]/document` route** — rendes auth + tulajdonjog-ellenőrzés. Ez a minta hiányzik az AI route-okból.
